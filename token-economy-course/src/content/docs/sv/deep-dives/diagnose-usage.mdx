:::note[Valfri fördjupning]
Det här är ett valfritt deep-dive för dig som vill undersöka oväntat hög förbrukning. Det är inte obligatorisk läsning och behövs inte för att följa huvudspåret.
:::

## 1. Vad det här deep-dive:t täcker

Det här momentet hjälper dig att gå från ett symtom till en rimlig hypotes. Du får en metod för att undersöka fler återförsök, växande sessionskostnad och skillnader mellan liknande uppgifter. Du får också en grund för att läsa cacheinformation och tolka mätvärden utan att dra för stora slutsatser.

Det här är inte en exakt prisberäknare och inte en garanti för hur en viss tjänst räknar credits. Visningen, detaljnivån och definitionerna kan skilja sig mellan planer, modeller och verktyg. Använd därför din miljös egna uppgifter som observationer och kontrollera aktuella villkor hos tjänsten.

## 2. Vanliga symtom och vad de kan peka på

Börja med att beskriva vad som faktiskt har förändrats:

| Symtom | Möjliga förklaringar att undersöka |
| --- | --- |
| Fler omtag eller återförsök | Otydlig uppgift, felaktig kontext, testfel eller en modell som behöver flera korrigeringar |
| En session blir successivt dyrare | Växande historik, fler verktygsresultat eller stora filer som följer med mellan turerna |
| En liten ändring ger oväntat stor förbrukning | Bred kontext, extra instruktioner, längre output eller arbete utanför den synliga ändringen |
| Samma uppgift varierar mycket | Olika modellval, arbetsläge, startläge, cacheträff eller slump i resultatet |
| Hög förbrukning utan längre svar | Stor input, många verktygssteg eller återförfrågningar snarare än längre output |

Se tabellen som hypoteser, inte diagnoser. Ändra en sak i taget om du vill jämföra med en baslinje.

## 3. Så använder du Agent Debug Logs

Detaljerade loggar är användbara när den vanliga användningsvyn inte förklarar skillnaden. Börja med en specifik session och notera uppgiftens startläge, modell och ungefärliga antal turer. Titta sedan efter:

- hur många modellförfrågningar som gjordes,
- vilka verktygsanrop och resultat som följde,
- om samma instruktioner eller filer återkom,
- om fel ledde till återförsök,
- hur input och output förändrades mellan turerna.

Jämför helst två liknande uppgifter: en normal session och en session med hög förbrukning. Fråga inte bara ”vilken rad kostade mest?” utan också ”vilket arbetsflöde skapade de extra turerna?”.

1. Bekräfta att sessionerna är jämförbara.
2. Räkna turer, verktygssteg och återförsök.
3. Leta efter växande kontext eller upprepade resultat.
4. Kontrollera cacheinformationen.
5. Formulera en liten ändring och testa igen.

## 4. Grunderna i cacheanalys

Cacheanalys kan visa om delar av återkommande input återanvändes. En hög cacheträff kan betyda att mycket av materialet var oförändrat; en låg träff kan betyda att kontexten ändrades, att materialet inte kunde återanvändas eller att tjänsten använder andra regler.

Cacheträff är inte samma sak som låg total kostnad. En session kan återanvända mycket input men ändå bli dyr genom många turer, stor output eller återförsök. Jämför därför cacheinformation med antal förfrågningar, input, output och resultatkvalitet.

## 5. Mätvärdenas begränsningar

Mätvärden berättar vad en viss vy eller logg registrerade. De berättar inte alltid varför arbetet behövde göras eller om resultatet blev bra. Credits kan påverkas av modell, plan, arbetsläge, cache, verktyg och intern hantering som inte syns i gränssnittet.

Använd siffror för att hitta mönster, inte för att låtsas ha mer precision än underlaget ger. Skriv exempelvis ”den här sessionen hade fler turer och lägre cacheträff” innan du skriver ”cachemissen orsakade hela ökningen”. För den senare slutsatsen behöver du en kontrollerad jämförelse.

## 6. Säkerhetsnotis

Agent Debug Logs kan innehålla kod, filsökvägar, promptar, instruktioner, verktygsresultat och annan känslig information. Dela dem inte okontrollerat i chattar, ärenden eller publika forum.

Maska hemligheter, personuppgifter, kunddata och proprietär kod innan du delar ett utdrag. Begränsa också utdraget till de rader som behövs för frågan. Förvara loggar enligt organisationens regler och radera kopior som inte längre behövs.

**Kort sagt:** börja med symtomet, jämför likvärdiga sessioner, använd loggar och cache som ledtrådar och behandla alla loggar som potentiellt känsliga.
