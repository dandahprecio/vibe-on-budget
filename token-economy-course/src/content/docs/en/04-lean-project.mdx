# Bygg ett snålt projekt

In the last module you compressed your prompts. Now we turn to something that costs you tokens without you noticing: your instruction files.

VS Code automatically includes `.github/copilot-instructions.md` (and any `AGENTS.md` files) in every chat request. That's smart — until the file grows. A 1000-line instruction file becomes 500+ tokens deducted from your account every time you press Enter.

👉 _New to instruction files? [Read VS Code's guide](https://code.visualstudio.com/docs/agent-customization/custom-instructions)._

In this module you'll build a project that's lean by default: short instructions, files that load only when needed, and a workspace that doesn't feed the agent noise.

---

## Mätning före/efter 🟢

Innan du ändrar något: notera din dagsförbrukning i dashboarden. Gör ändringarna. Jämför efter en vecka.

Mät samma sak före och efter — till exempel använda tokens per dag, antal requests eller kreditförbrukning. En förbättring som inte syns i din egen användning är bara en teori.

## Den alltid-på-skatten 🟢

De här filerna kan automatiskt användas som kontext eller bli tillgängliga för arbetsytans sökning, beroende på verktyg och konfiguration:[^m4-1][^m4-2]

| Fil eller källa | När den laddas | Roll |
|---|---|---|
| `.github/copilot-instructions.md` | Automatiskt när stöds | Gemensamma instruktioner för repot |
| Öppna editorflikar | Kan läggas till som kontext | Aktiva arbetsfiler |
| VS Code-inställningar | När funktionen läser dem | Beteende och gränser |

*(Se [Glossary](/vibe-on-budget/en/glossary) för definitioner av alltid-på-skatt, lazy loading och AGENTS.md.)*

The key is simple: every instruction that's "nice to have" but not needed right now is a cost on every request.

:::tip[Want to know more?]
VS Code has [detailed documentation on instruction files](https://code.visualstudio.com/docs/agent-customization/custom-instructions) — how they work, where to place them, and the difference between `.github/copilot-instructions.md`, `AGENTS.md`, and `CLAUDE.md`.
:::

## 1. Always-on instruction files

`.github/copilot-instructions.md` is VS Code's default. But there are two other filenames that do the same thing — they're loaded automatically in every request:

| File | Tool | Role |
|---|---|---|
| `.github/copilot-instructions.md` | VS Code (Copilot) | Default — use this if you only run Copilot |
| `AGENTS.md` | Copilot, Claude Code, Codex CLI | Cross-tool — works across multiple agents |
| `CLAUDE.md` | Claude Code, Anthropic | Claude-specific instructions |

**Pick one.** If you have all three you risk duplicates and paying for the same instructions multiple times. Only using Copilot? Go with `.github/copilot-instructions.md`. Does your team switch between agents? `AGENTS.md` covers more.

De flesta team fyller filen med arkitektur, stilguider och allmänna principer. Allt kan skickas som systemkontext — även när frågan bara handlar om att byta namn på en variabel.

### Minimal mall: kod + språk

```markdown
# Output format
- Code blocks only. Strip prose, greetings, explanations.
- Replace unchanged code with: // ... existing code ...
- No markdown text outside the code block.

# Language
- English for all prompts and responses
```

Det här är ungefär 40 tokens. Den täcker bara regler som verkligen ska gälla brett.

### Medium-mall: balanserad

```markdown
# Output format
- Code blocks only. Strip prose, greetings, explanations.
- Replace unchanged code with: // ... existing code ...

# Language
- English for all prompts and responses

# Project context
- Framework: Astro 5 + Starlight
- Package manager: npm
- Tests: Vitest with @testing-library/dom
- No TypeScript — use JSDoc for types
```

Använd medium-mallen när lite projektkontext faktiskt förbättrar svaren. Lägg inte hela projektets dokumentation här.

### Lägg inte detta här

- ❌ API-nycklar eller andra hemligheter — de skickas till modellen.
- ❌ Flersidig arkitekturdokumentation.
- ❌ Full dokumentation för komponentbibliotek.
- ❌ Allmänna konventioner som “vi skriver ren kod”.
- ❌ Gamla beslut som inte längre gäller.

:::caution[Instruktionsbloat är permanent skuld]
Varje rad i `copilot-instructions.md` betalas på varje request av varje teammedlem. En fil på 1000 rader kan kosta 500+ tokens per request i tusentals requests per dag.
:::

### 200-radersgränsen 🟡

Instruktionsfiler växer nästan alltid. Chakrabarti et al. observerade **+226 %** livstidsökning i en studie av instruktionsfiler i publika repositoryn.[^m4-3] Daniel Vaughan tolkar resultatet som ett underhållsproblem och rekommenderar en praktisk gräns på ungefär 200 rader.[^m4-4]

> 200 rader är praktisk vägledning från Vaughans analys — inte ett resultat som originalstudien själv fastställer. Originalstudien rapporterar en median på 39 instruktioner och 90:e percentilen på 131.[^m4-3][^m4-4]

- **Runt 200 rader** är en underhållsgräns, inte en garanti för modellens kontext.[^m4-4]
- **Tokenkostnaden** växer med antalet requests. Mät faktisk input och output för din modell och ditt arbetsflöde i stället för att lita på ett universellt estimat.[^m4-5]

<Steps>
1. Räkna rader och tokens i dina instruktionsfiler.
2. Flytta ämnesspecifika regler till skills eller `.prompt.md`-filer.
3. Behåll alltid-på-lagret så kort att en människa kan läsa om och rensa det i ett svep.
</Steps>

:::note[What are .prompt.md files and skills?]
Both are ways to move rules *out* of `copilot-instructions.md` so they don't cost tokens on every request:

- **[`.prompt.md`](https://code.visualstudio.com/docs/agent-customization/prompt-files)** — a file you `#`-mention in chat when you need it. You decide when it loads.
- **[Skills](https://code.visualstudio.com/docs/agent-customization/agent-skills)** — instructions the agent recognizes and activates for the right task. Automatic, but only when it matches.

Choose `.prompt.md` for rules you want control over. Choose skills for patterns that repeat often.
:::

### Prompt comments: save the why 🟡

Instructions grow because the original **why** disappears. When no one remembers what problem a rule was supposed to fix, removing it feels risky — even if the problem is long gone.

**So how do we document why a rule exists?** Two ways — one quick, one robust.

**Method 1: Comment in the file**

Write a short note right after the rule explaining what happened, what you thought would help, and what the result was:

```markdown
# .github/copilot-instructions.md

# Output format
- Code blocks only. Strip prose, greetings, explanations.
<!-- 2026-06: Verbose responses burned 3x output budget.
     Fix: code-only output. Result: 62% fewer tokens. Keep. -->
```

The research backs this up: Chakrabarti et al. found that prompt comments reduced excessive instruction growth by **99.3%** in the evaluated environment.[^m4-3]

A warning: HTML comments are handled differently by different tools. Daniel Vaughan reports that [Codex CLI](https://github.com/openai/codex) filters out comments before sending them to the model, while a [Claude Code issue](https://github.com/anthropics/claude-code/issues/83899) shows that comments can be sent verbatim.[^m4-4][^m4-6] In other words: don't assume the comment is invisible to the agent — keep it short and factual.

**Method 2: Separate logbook (recommended)**

For a more robust solution, keep an `instructions-log.md` that's only for humans:

```markdown
# instructions-log.md

## 2026-06 — Code-only output
- Problem: verbose responses burned 3x output budget
- Rule: "Code blocks only. Strip prose, greetings, explanations."
- Effect: 62% fewer output tokens
- Status: keep
```

The logbook is never sent to the agent — unlike HTML comments, this is a file you fully own. Link to it from `copilot-instructions.md`. The risk: if you don't update the logbook when you change a rule, it falls out of sync. Make it a habit — update both in the same commit.

## 2. Lazy loading med `.prompt.md` och skills 🟡

Lägg inte alla regler i det automatiska lagret. Skapa specialiserade filer som du laddar först när uppgiften behöver dem.[^m4-7]

| Fil | Innehåll | Använd när |
|---|---|---|
| `frontend-style.prompt.md` | CSS-konventioner och komponentmönster | Du bygger UI |
| `db-schema.prompt.md` | Tabeller och relationer | Du skriver queries |
| `testing.prompt.md` | Testkonventioner och mockmönster | Du skriver tester |
| `.github/skills/frontend/SKILL.md` | Återanvändbar arbetsmetod | Du arbetar med frontend |

Here's how they might look in practice:

<Tabs>
<TabItem label=".prompt.md">

```markdown
---
name: frontend-style
description: >
  Frontend component conventions, Tailwind
  styling, responsive patterns, and common
  pitfalls.
---

# .github/prompts/frontend-style.prompt.md

## Component conventions
- Use PascalCase for component names
- One component per file
- Props interface at top, exported

## Styling
- Tailwind utility classes only — no custom CSS
- Responsive: mobile-first, breakpoint sm → lg → xl
- Dark mode: use `dark:` prefix

## Known pitfalls
- Avoid nested ternary in JSX — extract to variable
- Don't mix controlled/uncontrolled inputs
```

</TabItem>
<TabItem label="Skill">

```markdown
---
name: frontend-ui
description: >
  Component design, Tailwind styling,
  responsive layouts, and accessibility.
---

# .github/skills/frontend/SKILL.md

## When to use
- Building or refactoring UI components
- Reviewing components for accessibility
- Debugging layout or responsive issues

## Conventions
1. Prefer composition over inheritance
2. Extract repeated patterns into shared components
3. Every interactive element needs `aria-label` or visible text

## Output format
- Return the component code, no explanation
- Include Tailwind classes inline
```

</TabItem>
</Tabs>

Reference a prompt file in chat like this:

```text
/frontend-style Review this signup form for accessibility gaps
```

Prompt files are loaded on demand via slash commands or `#`-mentions — unlike custom instructions they don't cost tokens on every request.[^m4-7]

Skills work a bit differently. You can invoke them manually with a slash command:

```text
/frontend-ui Build a responsive card grid with hover states
```

But the real power is that the agent can also activate them automatically — when your task matches the skill's `description`, the agent loads it without you asking.

:::tip[Want to know more?]
Read VS Code's guides on [creating prompt files](https://code.visualstudio.com/docs/agent-customization/prompt-files) and [building skills](https://code.visualstudio.com/docs/agent-customization/agent-skills).
:::

## 3. Uteslut brus med native VS Code-inställningar 🟢

VS Code-agenter kan använda workspace-filer som kontext. Uteslut sådant som aldrig hjälper uppgiften: byggartefakter, beroenden, mockdata, loggar och stora genererade filer.[^m4-8]

Använd tre lager:

- **`.gitignore`** — håll genererade filer och beroenden utanför Git. Det påverkar också workspace-sökning, men en fil som redan är öppen kan fortfarande kringgå detta lager.
- **[`files.exclude`](https://code.visualstudio.com/docs/configure/settings#:~:text=to%20set%20the-,files.exclude,-setting%20to%20exclude)** — dölj filer från Explorer och relaterade vyer.
- **[`search.exclude`](https://code.visualstudio.com/docs/configure/settings#:~:text=files.exclude%20and-,search.exclude,-use%20glob%20patterns)** — ta bort filer från sökresultat utan att dölja dem i Explorer. Det är den rekommenderade vägen när målet är lägre tokenförbrukning från agentsökning.[^m4-8]

Lägg till projektets relevanta mönster i `.vscode/settings.json`:

```json
{
  "search.exclude": {
    "dist/**": true,
    "build/**": true,
    "node_modules/**": true
  },
  "files.exclude": {
    "**/mock-data/**": true
  }
}
```

Exempel på lämpliga kandidater är byggmappar, `node_modules`, mockdata, loggar, stora lockfiler och genererad kod. Dölj inte källfiler som agenten behöver för att förstå projektet.

:::caution[Inte en säkerhetsgräns]
Exkludering minskar kontext och brus. Lägg aldrig API-nycklar eller andra hemligheter i workspace-filer och behandla inte exkluderingsinställningar som en ersättning för riktig secret management.
:::

For inline completions, keeping related files open in tabs helps — but in agent mode, the agent reads the files it needs on its own.

## 4. Hantera sessioner som en snål arbetsyta 🟢

The longer a session runs, the more context is sent with every request. Previous prompts, responses, and files eat into your token budget — even when they're no longer relevant. Here's how to keep your history lean.[^m4-1]

| Situation | Gör så här | Varför |
|---|---|---|
| Samma uppgift, flera steg | Stanna i sessionen | Agenten kan använda relevant beslut och kontext |
| Samma uppgift, men kontexten är stor | Kör `/compact` | Äldre kontext sammanfattas och frigör utrymme |
| Uppgiften är klar | Starta en ny session | Nästa uppgift behöver inte bära gammal historik |
| Du byter ämne | Starta en ny session | Blanda inte två problem i samma kontext |
| Du vill behålla ett beslut mellan ämnen | Sammanfatta beslutet manuellt och klistra in i ny session | Du tar med signalen, inte hela historiken |

Exempel:

```text
/compact focus on the API design decisions
```

Använd `/compact` för att fortsätta samma arbete. Starta en ny session för ett nytt ämne — komprimering och ny session löser olika problem.[^m4-1]

## 5. Set limits on the agent's appetite 🟡

Set a limit on how many requests the agent can make before VS Code stops and asks if you want to continue:

```json
{
  "chat.agent.maxRequests": 25
}
```

The default is 25. This is your guardrail against the agent going off track and burning tokens — when the limit is hit, you get to decide whether it's on the right path or should start over. Lower it if you often do small, simple changes. Raise it if you regularly work on larger refactorings.

Another way to save tokens: enable output compression for terminal commands:

```json
{
  "chat.tools.compressOutput.enabled": true
}
```

Strips out install logs, unchanged diff hunks, and other noise from terminal output before it's sent to the model.

## 6. Don't let AI write your instructions ⚠️

Write and trim your instructions yourself. AI doesn't know your project's real pain points better than you do. LLM-generated instructions can add obvious advice, repeat documentation, and bloat the always-on context you're trying to keep lean.

GitHub themselves recommend avoiding "AI-generated guidance that doesn't reflect your actual system" and warn against instructions that make the context noisy.[^m4-10] Chakrabarti et al. observed +226% lifetime growth in instruction files — a trend that AI-generated additions only accelerate.[^m4-3]

Feel free to ask AI to suggest a shorter version, but verify every line: what problem does the rule solve, and is the problem still real?

## Key Takeaways 🟢

- **Kort alltid-på-kontext** minskar en kostnad som annars återkommer i varje request.
- **Minimalmallen** innehåller bara kodformat och språk; medium-mallen lägger till nödvändig projektkontext.
- **Runt 200 rader** är en praktisk gräns för underhåll, inte en magisk modellgräns.
- **Promptkommentarer** bevarar varför en regel finns och gör rensning säkrare.
- **`.prompt.md`-filer och skills** laddas när de behövs i stället för alltid.
- **`.gitignore`, `files.exclude` och `search.exclude`** håller irrelevant workspace-kontext borta; `search.exclude` är bäst för tokenbesparing.
- **Färre öppna tabs och tydliga sessioner** minskar historik och kontextbrus.
- **Mät före och efter** — din dashboard är facit för ditt arbetsflöde.
